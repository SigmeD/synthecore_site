## Контроль перед merge

- Подтверждены чистая рабочая папка и актуальный `origin/main` (`67f75cd` до слияния), являющийся предком согласованной сборки. Тестовое дерево слияния совпадает с деревом feature-ветки; конфликтов нет.
- Повторный `node --test scripts/test-static-checks.cjs scripts/test-shared-site.cjs`: 75/75. Build `--check`, 17 raw motion SHA, 25 файлов v27 и семь секций проверены повторно в Git blobs.
- Исходная матрица на неизменном runtime: 372/372 motion-проверок, 295/295 оболочки/каталога, ноль отличий выбранных метрик оболочки на шести размерах. Перед merge повторяется десктопный и мобильный браузерный прогон; актуальные логи сохраняются в локальном `output/merge-v62` и в описании PR #6.
- Полный архивный `--strict` для композиции с оболочкой v27 не является проходным критерием: локальный исторический результат 423/437 и исключения явно сохранены. Manifest не подменяется; защищённые motion SHA должны совпадать всегда.

Автоматический wheel/touch не доказывает субъективную плавность физической мышью/тачпадом. Разрешение владельца на merge не записывается как доказательство прохождения такого ручного теста. Firefox/WebKit и реальные мобильные устройства остаются вне выполненной матрицы.

## После merge

Получить `origin/main`, проверить, что runtime-дерево совпадает со слитой feature-веткой, повторно проверить Git blobs и статические тесты, затем синхронизировать локальный `main` fast-forward с `core.autocrlf=false`. Это сохраняет raw SHA motion-файлов, часть которых содержит исходные CRLF. Локальные `/` и `/raboty/` должны обслуживать ту же сборку.

Публикация и последующие изменения хедера/футера/анимаций требуют отдельных задач. Для отката возможного merge использовать новый PR с revert merge-коммита; не переписывать общую историю.
