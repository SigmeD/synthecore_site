## Проверки текущего checkout

Выполнять из корня репозитория, нужны Node.js и Git:

```powershell
node scripts/verify-v62-import.cjs
node docs/qa/v62-on-v27/verify-git.cjs HEAD
node scripts/build-site.cjs --check
node scripts/check-project.cjs
node scripts/verify-works-static.cjs
node scripts/verify-services-static.cjs
node scripts/check-hero-geometry.cjs
node scripts/verify-sticky-handoff-v61.cjs
node --test scripts/test-static-checks.cjs scripts/test-shared-site.cjs
git ls-files --cached --others --exclude-standard | node scripts/check-doc-links.cjs
```

`verify-v62-import.cjs` по умолчанию проверяет 17 защищённых файлов на диске **по исходным байтам**, включая LF/CRLF. `verify-git.cjs HEAD` проверяет Git blobs коммита, без аргумента — индекс. Проверка HEAD не видит незакоммиченные изменения. Контракт v27 нормализует окончания строк текстовых файлов до LF, шрифты проверяет по raw-байтам; содержательные секции главной также сравнивает после нормализации LF. `build-site.cjs --check` ничего не генерирует.

`verify-v62-import.cjs --strict` сравнивает весь исходный архив, включая его документацию и самостоятельную оболочку. Такой состав отличается от принятой композиции v62 + v27. [423/437](strict-check.txt) и [исключения](strict-exceptions.json) — снимок рабочего каталога при импорте, а не ожидаемый результат после документационных изменений или другого checkout. Оригинальные hash manifests сохраняются; подгонять их под текущий состав запрещено.

## Браузерная проверка без внешних эталонов

Нужны установленный Playwright и его Chromium. Скрипты ищут пакет в проекте либо в профиле пользователя; runtime сайта npm-пакетов не требует. Сначала запустить локальный сервер в отдельном терминале:

```powershell
pwsh -NoProfile -File .\start-local.ps1 -Port 4176 -NoBrowser
```

Затем из корня проекта:

```powershell
$env:SYNTHECORE_URL = 'http://127.0.0.1:4176/'
node docs/qa/v62-on-v27/catalog.cjs
```

Этот сценарий проверяет обе страницы текущей сборки. Результаты пишет в `output/v62-on-v27/catalog/`, существующие результаты нового запуска могут быть заменены. Порт launcher по умолчанию — 4173; 4176 — явно выбранный адрес последнего локального просмотра.

## Сравнение с исходными сборками

Сценарии [motion.cjs](motion.cjs) и [shell.cjs](shell.cjs) используют фиксированные порты и требуют локальных эталонов. Переменная `SYNTHECORE_URL` их адреса не меняет. [serve.cjs](serve.cjs) обслуживает:

| Порт | Каталог относительно корня | Назначение |
|---|---|---|
| 4180 | `output/worktrees/works-v27` | v27, коммит `0849711f39f838971bc4e5a732cee0a13ed5917b` |
| 4181 | `.` | Проверяемая сборка |
| 4182 | `output/v62-source` | Распакованный оригинальный архив v62, с `index.html` непосредственно в этом каталоге |

Каталоги `output/` и исходный ZIP не поставляются с клоном. В текущей рабочей папке v27 сохранён в detached worktree. Не перезаписывайте существующие reference/worktree-папки: проверьте их состояние через `git worktree list` и контрольные суммы. Для отсутствующих эталонов потребуется исходный ZIP и экспорт коммита v27; создание нового worktree требует согласия владельца по правилам проекта. SHA-256 переданного ZIP: `2169bdac56210c3d5f4874b1147be0b2bf6958f14af941d175589502be9e7b0a`.

Когда все эталоны готовы и порты свободны, в отдельном терминале:

```powershell
node docs/qa/v62-on-v27/serve.cjs
```

Потом из корня проекта:

```powershell
node docs/qa/v62-on-v27/motion.cjs
node docs/qa/v62-on-v27/shell.cjs
```

Motion пишет в `output/v62-on-v27/motion/`, shell — в `output/v62-on-v27/shell/`. Для узкого повтора motion поддерживает `--only=1440x900` либо `--only=390x844`; это не полный прогон. Оба размера включают сравнение с архивом на 4182. Публикуемые доказательства в этом каталоге не обновляются автоматически: новый результат сначала проверяют и явно включают в отдельный PR.
